# Silky app

Express + Postgres (Drizzle) backend in `server/`, the Astro project in `storefront/` (public storefront in French and Arabic, and the admin panel at `/admin`; paths below that start with `src/` inside the Astro sections are relative to `storefront/`). There is no Vite app any more; the API serves no pages (`GET /` answers `{ ok: true }`). ESM everywhere (`"type": "module"`).

## Repository layout (two independent apps)
- `server/` (API) and `storefront/` (Astro: shop + admin) are separate projects, each with its own `package.json`, lockfile, `node_modules` and `.env`; they are deployed separately (Render, Cloudflare) and talk over HTTP only. **Neither imports a file of the other.** The root holds only docs, `integration/` and `.claude/`.
- `shared/` (pure modules) exists twice, `server/shared` and `storefront/shared`, byte for byte identical. After changing one, copy it to the other and run `node integration/check_shared_in_sync.mjs`.
- `integration/` is the only place that may touch both apps: `check_independence.mjs` (fails if a relative import or file path crosses between `server/` and `storefront/`), `check_shared_in_sync.mjs`, and the helpers/tests that need the API and the storefront together (`test_rendered_pages.mjs`, `serve_fixtures.mjs`, `serve_admin_session.mjs`, `test_admin_orders_pdf_selection.js`). Neither app imports from it.
- Commands run inside the app folder (`cd server && npm run dev`, `cd storefront && npm run dev`); `node server/scripts/test_*.js` from the repository root also works. Server config files that were at the root (`.env`, `.env.example`, `drizzle.config.js`, `package.json`) are in `server/`; the e-mail logo is `server/assets/logo.png`. Node 24 locally (global `fetch`, `FormData`).

## Orders
- Statuses (`orderStatusEnum`, `server/models/orders.model.js`): pending, processing, completed, delivered, cancelled, exchanged, refunded. "Confirmed" in the UI is stored as `completed`. `processing` is shown as `pending` by `formatOrder`.
- Every confirmation path (`POST /orders/:id/confirm`, `/orders/bulk-confirm`, `PATCH /orders/:id/status` with `completed`, `/orders/bulk-status`) ends in `confirmOrder` in `server/services/order.service.js`. It only flips pending/processing to completed under `SELECT ... FOR UPDATE`. Stock is decremented at order creation, not at confirmation.
- Draft conversion (`draftService.confirmDraftAsOrder`) creates a `pending` order through `createManualOrder` and never calls `confirmOrder`.
- `confirmOrders` (bulk) runs sequentially and swallows per-order errors.
- Money is `numeric(10,3)` TND, parsed with `parseFloat`. The amount to collect for a plain order is `calculateOrderCustomerAmountToPay` in `server/repositories/order.repository.js` (= stored `total_amount`). Exchanges and refunds have their own `customerAmountToPay`. Delivery fee is stored per order.
- Governorates: `orders.governorate_id` FK, 24 canonical rows in `server/config/governorates.js` (unaccented Latin names). Phone is exactly 8 digits.

## Conventions
- Layering: routes -> controllers -> services -> repositories -> `server/models`. Transactions use `runInTransaction` (`server/repositories/transaction.repository.js`).
- Errors: `AppError(message, status)` + `sendError` (`server/utils/errors.js`); response shape `{ error }`; user messages are mostly French.
- Auth: Bearer JWT. Admin routes use `[authMiddleware, adminMiddleware]`. `/api` runs `guestSessionMiddleware`, which sets a cookie.
  - `authMiddleware` / `optionalAuthMiddleware` check the token against the `users` row on every request: the account must exist, the role is the stored one (a demoted admin loses access at once), and tokens issued before `users.tokens_valid_after` are refused (admin logout, every password change/reset; one-second precision; `changePassword` returns a fresh `token`, which `api.changePassword` stores). Customer logout stays client-only. A test that signs a token by hand needs a real user row and the `sub` claim (`server/scripts/helpers/test_accounts.js`).
  - `server/utils/asyncErrors.js` (imported first in `app.js`) sends errors thrown or rejected in async handlers to the error handler; without it a bad body type hangs the request. Uploads: the stored extension comes from the declared MIME type and the first bytes must match it (`server/utils/fileSignature.js`, `verifyImageUpload` / `verifyVideoUpload` after multer on every upload route); `/uploads` is served with `Content-Security-Policy: sandbox`. Basic headers and the page Content-Security-Policy in `server/middleware/securityHeaders.js` (`CSP_MODE`: `report-only` by default, `enforce` only after browsing the site with no report; a new third-party script, font or embed must be added to its policy).
  - Production start-up refuses a missing `DATABASE_URL`, `JWT_SECRET`, `CORS_ALLOWED_ORIGINS`, or an `ADMIN_PASSWORD` that is a placeholder or under 10 characters. `TRUST_PROXY` (hop count, unset locally) makes `req.ip` the visitor behind a reverse proxy. Security regression suite: `node server/scripts/test_security_audit.js` (silky_test only).
- Config: `server/config/env.js` (dotenv); document every var in `server/.env.example`; `server/.env` is gitignored.
  - `NODE_ENV` must be `production`, `development` or `test`; anything else stops the server at start. `EXPOSE_RESET_TOKEN=true` (development only, ignored in production) makes the forgot-password answer carry the reset token when no `SMTP_USER` is set.
  - E-mail (`resolveMailMode` in `server/services/email.service.js`): `RESEND_API_KEY` set = Resend over HTTPS (wins over SMTP; `createResendTransport`, inline logo as `content_id`, `RESEND_API_URL` only for tests; Render's free plan blocks the SMTP ports, so production there uses Resend; `EMAIL_FROM` must be on a domain verified in Resend); else SMTP credentials set = real SMTP; none in development = Ethereal fake inbox; none in production = sending fails with a clear message (never Ethereal). Test: `node server/scripts/test_email_resend.js` (fake local Resend, no network). The `reply_to` key of Resend's API is unconfirmed against the live service: check one real mail's Reply-To.
  - `server/utils/processSafety.js` (installed by `server/index.js` only) logs unhandled rejections and exits on an uncaught exception; the database pool has an error listener and a 30 s connection timeout.
- Base styles: `storefront/src/styles/reboot.css` holds the element-level rules of Bootstrap 5.3.8 (copied verbatim, MIT notice kept in the file); the CDN stylesheet is gone. It must stay the first stylesheet of the storefront so the shop's own CSS keeps overriding it. Do not add Bootstrap classes or reload the CDN file: before removal a before/after comparison of every element's computed styles over 47 views (storefront fr/ar, phone, admin, cart states) showed zero difference.
- New environment from scratch: `server/db/schema.sql` (generated by `npm run db:export-schema` from a migrated database; regenerate it after every new migration, `test_deploy_readiness.js` fails on drift) is applied by `npm run db:init`, which refuses any non-empty database. Startup migrations only extend existing tables and fill the governorates. `npm run admin:create` inserts only the admin row. `npm run preflight` is the read-only readiness check (configuration, files, schema, admin, leftover test data, missing image files). `GET /health` answers 200 only while the database does. One log line per request (`server/middleware/requestLogger.js`, on in production). Pool size and timeouts come from `DB_POOL_MAX`, `DB_CONNECTION_TIMEOUT_MS`, `DB_STATEMENT_TIMEOUT_MS`. `add_governorates.js` refuses to delete orders unless `ALLOW_ORDER_RESET=yes`. How to deploy, back up, restore and roll back: `DEPLOYMENT.md`.
- Schema changes: idempotent startup migrations in `server/db/migrations/add_*.js`, registered in `server/index.js`. drizzle-kit is not the real migration path; its baseline is stale, so do not run `db:generate` or `db:push`.
- Uploads (photos, videos) go through `server/services/storage.service.js` (`putObject` / `deleteObject` / `objectExists` / `objectSize`, key `uploads/<file>`), chosen by `STORAGE_DRIVER=disk|r2` (default disk = `UPLOADS_DIR`, served by the API at `/uploads`; `r2` = Cloudflare R2, the API then serves no `/uploads`, `MEDIA_PUBLIC_URL` is the public address, `r2` without its four `R2_*` variables stops the server). Photos are kept in memory by multer (25 MB), checked (`verifyImageUpload` also names the file), resized, and stored copies first, original last (`createResizeMiddleware` in `server/utils/imageVariants.js`); videos (200 MB) go to a temp file and are streamed to the storage (`storeUploadedVideo`). Deleting a photo or video calls `deleteObject` for the file and its three copies. `node scripts/copy_uploads_to_r2.js` (inside `server/`; `--dry-run`, `--verify`) copies an existing uploads folder to R2 and cross-checks the database references. Test: `node server/scripts/test_storage_service.js` (fake R2 client, no network).
- PDFs are generated client-side only (`storefront/src/admin-app/utils/orderPdf.js`).
- Do not make external HTTP calls inside a DB transaction. Post-commit external side effects follow the claim-row pattern in `dispatchOrderConfirmationEmail`.

## Variants
- The order of a product's variants (size buttons, preselected size) is `product_variants.position`, set when the product is created or saved (index in the variants list built from the editor's colours and sizes, colour by colour) and never touched by stock changes. `findById` and `findAll` sort by it (NULL last, then `created_at`). Migration `add_variant_position.js` numbers products that have none (colours by first photo, sizes in natural order). Any new code that inserts a variant must set `position`.
- `productRepository.findAll` loads the whole list in four queries and returns exactly what `findById` returns per product; `orderRepository.findAll` does the same for orders (`test_list_loading.js`). It excludes hidden products unless `includeHidden: true`.

- Product photo alt text: `products.image_alt` / `image_alt_ar` (migration `add_product_image_alt.js`), one custom text per product for all its photos, set in the admin product form and the inline editor. `productCustomAlt(product, locale)` (`shared/productText.js`) returns it (Arabic falls back to French); empty means the generated `productImageAlt` (name, colour, position). Test: `node server/scripts/test_product_image_alt.js` (silky_test only).

## Public URLs and SEO
- A product's address is `/product/<slug>` (`products.slug`, made from the name at creation, kept when the name changes; `productPath(product)` in `shared/urls.js`). The id still works: the storefront answers one 301 to the slug address (`src/lib/pages/load.ts`) and replaces the URL. Build links with `productPath`, never `/product/${id}`.
- `PRE_PRODUCTION.md` (repo root) lists what must change before going live; add to it when you find something.

## Tests
- No test framework. Standalone scripts `server/scripts/test_*.js` run with `node <file>`, import the real `app`, listen on an ephemeral port, use a real Postgres via `DATABASE_URL`, and exit non-zero on failure. `npm test` runs only `verify-phase3.js`.
- Mocks are hook-based (see `setMockOrderConfirmationSender` in `server/services/email.service.js`) or local mock HTTP servers.

## GOODEX delivery
- Parcel creation runs in `deliveryService.ensureParcelForOrder` (`server/services/delivery.service.js`), called by `confirmOrder` only after its transaction commits and only when that call changed the status. It never throws and never runs inside a transaction. Draft conversion does not create parcels.
- Exactly-once: the `order_deliveries` row (UNIQUE `order_id`) is the claim. States: creating | created | failed | unknown. `unknown` (timeout, 5xx, bad body, persist failure) is never re-sent automatically; admin retry needs `acknowledgeUnknown`.
- Real-provider gate: every request in `goodex.client.js` first passes `liveCallBlockReason` (`server/config/goodex.js`), which refuses (as a configuration error, nothing sent) unless the base URL is loopback (local mocks) or the run is opted in with `GOODEX_ENABLE_LIVE=true` AND is not a test run (`NODE_ENV=test` or a `DATABASE_URL` database name containing "test"). So a real token in `.env` cannot make legacy test scripts create real parcels. For the supervised sandbox/live check set `GOODEX_ENABLE_LIVE=true` on the dev server only. Test: `node server/scripts/test_goodex_live_guard.js` (hermetic, no DB).

- The only GOODEX HTTP code is `server/services/goodex.client.js`. `server/config/goodex.js` holds the official GOODEX status list (`GOODEX_STATUSES`, ids 1-20) with `resolveGoodexStatus`, credential checks (`missingApiConfig`, names only) and `resolveParcelGovernorate`. There is no governorate translation table: the saved governorate is validated against `CANONICAL_GOVERNORATES` and sent unchanged (GOODEX is stated to accept the same names; unconfirmed live). Missing credentials are reported as a configuration error before any data validation.
- Every parcel (order, exchange, refund) sends the product lines (`name (variant) xN`, joined by `, `, cut at 250 characters) in `remarque`; `designation` is never sent and there is no order/exchange/refund number in the request.
- `cod` = `calculateOrderCustomerAmountToPay(order)` formatted `NN.000`; `last_statut=12` is sent in the request (required). Requests carry `Accept: application/json` (as in the documented curl). The create response is read as the documented flat object (`id`, `ean`, `last_statut`, `created_at`, ...; no nested layouts are guessed): `ean` and `last_statut` drive the delivery, `id` and `created_at` are kept in `goodex_parcel_id` / `goodex_created_at` for troubleshooting. Error bodies (the documented 422 is a bare `{field: [messages]}` map) are summarized into `last_error`.
- Parcel guard: deliver (`deliverOrder`, so also PATCH/bulk status `delivered`), refund (`refundOrder`) and `createExchange` call `deliveryService.assertParcelCreated` inside their transaction and answer 409 while the order's parcel row exists and is not `created` (failed/unknown/creating) or one of its exchange parcels is failed/unknown. Orders with no parcel row (confirmed before GOODEX) stay allowed. The admin buttons mirror it (`parcelBlocked` in `AdminOrderCard.jsx`). Legacy non-GOODEX scripts (their fixtures can never produce a parcel) turn it off with `import './helpers/parcel_guard_off.js'` right after `import '../config/env.js'`; new tests that confirm orders and then deliver/refund/exchange need a working GOODEX mock or that import.
- Two independent statuses in the admin table: `Statut` (Silky order status) and `Statut livraison` (GOODEX, from `order.delivery`). GOODEX statuses never change an order's status, payment or totals (`Payé`/`Livré` are display only).
- Status ids: the numeric id is stored in `order_deliveries.goodex_status_id` and comes from POST `last_statut` (initially 12 = En Attente) or an integer `statut`. A textual `statut` (GET/webhook) gets an id only if its normalized text equals exactly one official label; anything else keeps the raw text with a null id and shows as `Statut non reconnu`. `Colis Introuvable` is not an official status: it sets `tracking_not_found_at` and never overwrites the saved status. It is recognized from the body at any HTTP code, and an HTTP 404 with an empty body or a JSON body without `statut` is also read as not-found (the PDF does not say whether 404 is used; an HTML 404 page or a 404 carrying a real status stays a tracking error). To confirm against real responses.
- Motif / incident: GOODEX sends `has_motif` (an indicator; the example uses numeric 0) and `motif` (text). `parseHasMotif` reads booleans, 0/1 and their string forms, anything else is unknown (null), never guessed. The flag is stored in `order_deliveries.has_motif`; an incident is displayed only when the parcel exists, a reason text was received and `has_motif` is not false (`incident` in `toPublicDelivery`, the single rule the UI uses). A webhook carries no flag (null). An omitted/empty motif never erases the stored text; an explicit false hides it, and a later non-empty reason without a flag re-opens it. Shown only in order details (`Incident de livraison`) plus a warning icon in the table.
- Refresh: the orders list reads saved data only (no GOODEX call). Explicit `Actualiser le statut` always calls GOODEX (GET). Opening details sends `onlyIfStale`, skipped for 10 minutes (`DELIVERY_REFRESH_COOLDOWN_MS`) after any poll/webhook/status update. Tracking errors return 502 and change nothing; a poll that started before the latest webhook is discarded. `status_received_at` records every successful status receipt (even an unchanged one), `status_updated_at` only changes of status, `last_webhook_at` / `last_polled_at` the sources; all four are shown in order details.
- Webhook: `POST /api/webhooks/goodex`, mounted in `server/app.js` before the guest-session middleware; Bearer `GOODEX_WEBHOOK_SECRET` (separate from `GOODEX_API_TOKEN`), fails closed when unset. The create/tracking/status contract now follows the GOODEX PDF text supplied in chat (not stored in the repo); the webhook payload contract (`code`, `statut` as text, optional `motif`, optional `test`, Bearer token, 2xx in under 3 s, up to 3 attempts, duplicates possible) is confirmed by the GOODEX webhook documentation (client.goodex.tn > webhook): the token is entered or generated in the GOODEX customer area together with our public https URL, which has a "Envoyer un appel de test" button; the status list contains no cancellation status, so a parcel cancelled at GOODEX may send nothing; there is no event timestamp, so ordering is arrival order (a poll that started before the latest webhook is discarded).
- Claims (tickets), documented in the GOODEX PDF text supplied in chat: `server/services/claims.service.js` + the claims block at the end of `goodex.client.js` + `order_claims` (local copy: GOODEX id, reference, status; GOODEX stays the source of truth). Admin routes in `server/routes/orders.routes.js` (`/orders/claims/*`, `/orders/:id/claims`).
  - Types come from `GET /api/v1/tickets/types` (the exact list GOODEX validates), cached 6 h in memory with a stale fallback; validation (`server/utils/claimValidation.js`) is driven by each type's `value_type` / `needs_value` / `message_required` (montant 85.000, telephone 8-20 digits, date YYYY-MM-DD today+, texte 5-255, message <= 1000), nothing hardcoded per type.
  - Opening (`POST /api/client/tickets`, `ean` only): HTTP 201 + ticket = created; HTTP 200 + `already_sent` = NOTHING created (answered 200, never shown as a creation, linked to the existing claim). GOODEX dedups open claims of the same type, so re-submitting after an uncertain outcome is safe. A parcel still `En Attente` is refreshed first and blocked locally if it still is (documented 422).
  - Cancel (`DELETE`): the live status is read first and only `nouveau` claims are cancelled (never merely `is_open`); it cancels the claim, never the parcel. Provider 401/403 are returned as 502, never as our own 401 (the frontend logs out on 401).
  - List is paginated (`data` + top-level pagination; default 20, Silky caps at 50 because the provider maximum is undocumented). Counters are used as returned (never recomputed) and cached 2 min; unconfigured answers `{configured:false}`. A claim never changes an order, its totals or the parcel.
  - UI: the order details only hold the "Nouvelle réclamation" form (`ClaimsBlock.jsx`). Listing, counters, status/EAN filters and cancelling live in Ventes > Réclamations (`storefront/src/admin-app/pages/AdminClaims.jsx`), fed by `GET /orders/claims/remote`; each listed claim also carries `localId` / `cancelled` / `canCancel` from the local copy (claims opened outside Silky have no `localId` and are read-only).
  - Unconfirmed against real responses: the detail layout (flat or `{ticket}` accepted), the wording of the "En Attente" 422, per-page maximum.
- GOODEX admin UI: delivery and claims render as cards built from one small kit, `storefront/src/admin-app/components/gx.jsx` (`GxButton` variants default/primary/danger/ghost, `Alert`, `KV`, `CopyButton`, `formatGoodexDate`) with `gx-` styles at the end of `admin.css`. Use them for new GOODEX screens. The cards span the full width of the order details row, exactly like the blocks above them (no width cap, no sticky positioning); the orders table keeps its horizontal scrollbar.
- Admin responses attach `delivery` via `deliveryService.attachDelivery`; `formatOrder` is intentionally untouched (it also serves customers).
- Audit tests (`node server/scripts/test_goodex_audit.js`, mock GOODEX, test DB only): admin authorization sweep over 22 routes, page loads send zero GOODEX requests, tracking failures never touch the saved status, webhook edge cases, config errors, no customer data or secrets in logs. A webhook `statut` of "Colis Introuvable" is handled like a tracking poll (flag only, never the saved status), and provider error text is redacted of the customer's name/phone/address before it is logged. Known limits: webhook payloads carry no timestamp, so a late retry of an older status overwrites a newer one until the next reconciliation or manual refresh; the webhook rate limiter keys on `req.ip` and `trust proxy` is not set (behind a reverse proxy all callers share one key). When running tests, set `GOODEX_ENABLE_LIVE=false GOODEX_BASE_URL=http://127.0.0.1:1` as a second guard.
- Log masking: `redactCustomerData` (`delivery.service.js`) masks the customer's name, phone (digit by digit, any separators), address and the exchange address parts in parcel-creation log lines, case-insensitively; the admin-visible `last_error` keeps the provider's wording. `POST /orders/:id/delivery/link` (admin API only, no button; the recovery path for a parcel that exists at GOODEX but was not saved, see the "Colis créé chez GOODEX (ean …) mais non enregistré" message) only accepts orders that are completed/exchanged/delivered, validates the code format and relies on the unique ean index; it does NOT verify the code with GOODEX and records the event as `create`.
- Background reconciliation (`server/services/delivery.reconciler.js`, started/stopped in `server/index.js` only, never in `app.js`): every `GOODEX_POLL_INTERVAL_MINUTES` (OFF by default: unset, `0` or an invalid value keeps it off; set e.g. `15` to enable it; first run 60 s after startup) it asks GOODEX (read-only GET) for the status of existing parcels and saves valid changes through `refreshDeliveryRow` (`delivery.service.js`, structured outcome, never throws; manual refresh shares `trackAndApply`). It imports no creation/retry/link function (a test greps for that). Eligibility (`deliveryRepository.findRefreshCandidates`, policy constants `RECONCILE_*` in `config/goodex.js`): state `created` with a well-formed ean, status not Payé(8)/Retour Payé(11) (Livré is NOT terminal, COD settles later), parcel younger than `GOODEX_POLL_MAX_AGE_DAYS` (60), any Silky order status (cancelling in Silky does not cancel the parcel). Spacing by last status change: under 48 h every cycle (gap = interval/2), up to 14 days every 3 h, then every 12 h; "introuvable" parcels: normal cadence for the first hour, then hourly for a day, then every 12 h, dropped after 14 days (manual refresh still works). Spacing uses `last_polled_at` only, so a webhook never shields a parcel from reconciliation. Batch `GOODEX_POLL_BATCH_SIZE` (50), concurrency `GOODEX_POLL_CONCURRENCY` (2), one run at a time per process. Stops: 401/403/config end the run; 429 ends it and pauses the scheduler for Retry-After (at least one interval); 5 consecutive network/server/timeout failures end it; a failing parcel is skipped for exponentially longer (in memory, max 6 h). Failed requests never change a saved status. No migration or index was needed (one row per parcel, bounded query). Log lines carry counts only. Single-instance design: with several instances enable it on one only (a second instance only doubles read-only requests). Test: `node server/scripts/test_goodex_reconciler.js` (mock GOODEX, injected timers and clock). The first poll of a parcel whose `has_motif` was never recorded writes one history event (has_motif null -> false).
- Tests: `node server/scripts/test_goodex_claims.js` (stateful mock of the claims API) and `node server/scripts/test_goodex_delivery.js` uses a local mock GOODEX server (`env.goodex.baseUrl`), no real credentials. It refuses to run unless the `DATABASE_URL` database name contains `test` (create one with `pg_dump --schema-only` plus the `governorates` rows; `ALLOW_NON_TEST_DB=1` overrides).
- Exchange parcels: every confirmed exchange gets its own GOODEX parcel. `exchangeService.createExchange` calls `deliveryService.ensureParcelForExchange` after its transaction commits (never throws, never calls `ensureParcelForOrder`; the exchange is final whatever GOODEX answers). The `order_deliveries` row of an exchange has `exchange_id` set (UNIQUE per exchange); the ordinary parcel has `exchange_id` NULL (partial UNIQUE on `order_id`), and `findByOrderId` / `claimNew` / `reclaim` only see ordinary rows. Migration `add_exchange_deliveries.js` also added `order_exchanges.decharge` (boolean); it is no longer written or read, the column only stays so existing databases and `schema.sql` do not change.
  - Fields: `echange=1`; `cod` = the exchange's `customerAmountToPay` as `formatOrder` shows it (productAmountAdded + deliveryFee, never the exchange total); `decharge=0` always (the exchange form no longer asks for it and the endpoint ignores any value sent). Governorate/address come from the exchange's `"Gov — street"` address (`resolveExchangeAddress`, accent-insensitive, no guessing). `remarque`/`nbre` mirror the ordinary parcel (the product lines; nbre = total quantity, unverified). No `gsm2`.
  - Admin: `exchanges[].delivery` is attached by `attachDelivery`; `POST /orders/exchanges/:exchangeId/delivery/{retry,refresh}` follow the order parcel rules (`unknown` needs `acknowledgeUnknown`). Webhooks find exchange rows by EAN like any other. Test: `node server/scripts/test_goodex_exchange.js` (mock GOODEX, test DB only).
- Refund parcels (Remboursement / Remboursement gratuit): every refund gets its own GOODEX parcel. `orderService.refundOrder` calls `deliveryService.ensureParcelForRefund` after its transaction commits (never throws; the refund and the `refunded` status are final whatever GOODEX answers). The `order_deliveries` row of a refund has `refund_id` set (UNIQUE per refund, migration `add_refund_deliveries.js`); the ordinary parcel now means `exchange_id IS NULL AND refund_id IS NULL`, so every ordinary-parcel query and the `ON CONFLICT` predicates carry both conditions. A row belongs to an exchange or a refund, never both.
  - Fields: `cod` = the refund's `customerAmountToPay` (`delivery_fee`: 8.000, or 0.000 for the free refund), `echange=0` and `decharge=0` sent explicitly (no return flag is documented by GOODEX; to be confirmed with them), `remarque` = the product lines like the other parcels, no `gsm2`. Name, phone and items come from the refund record; the address is the one `refundOrder` copied onto it: the latest exchange's `"Gov — street"` (`resolveExchangeAddress`) when the order has exchanges, otherwise the order's street plus the order's governorate. A missing/invalid governorate fails locally and nothing is sent.
  - Admin: `refunds[].delivery` is attached by `attachDelivery`; `POST /orders/refunds/:refundId/delivery/{retry,refresh}` follow the order parcel rules (`unknown` needs `acknowledgeUnknown`), shown in the refund history of the order details (`ParcelDeliveryLine`). The retry works on a `refunded` order. Webhooks and the reconciler find refund rows like any other. `assertParcelCreated` is not extended to refund rows (a refunded order is final). Test: `node server/scripts/test_goodex_refund.js` (mock GOODEX, test DB only).
- Test database admin: the admin panel login needs a user with `ADMIN_EMAIL` in `silky_test`; run `DATABASE_URL=postgres://.../silky_test node server/scripts/setup_test_admin.js` once (idempotent, refuses any non-test database). Never run `npm run db:seed` on a database you want to keep: it TRUNCATEs users, orders, products ... CASCADE (and its demo orders lack the required `governorate_id`).
- Known pre-existing failures (identical on the original commit, none GOODEX-related; ~18 legacy scripts): stale fixtures that violate today's validation (customer names with digits, missing governorate, orders inserted without `governorate_id`: e.g. test_buy_now, test_hardening_phase1, test_notifications, test_free_refund_economics, test_final_customer_payable_amount, test_product_deletion_safety), shared-DB pollution (test_refunds_and_stock_exchanges sums refunds left by other scripts), a stale expectation (test_email_system wants "SILKY", the template says "Silky"), an env-dependent check (verify-phase3 vs the CORS value in `.env`). On Windows with Node 24 a failing script can also crash on exit with a libuv assertion (exit code 127 instead of 1).
